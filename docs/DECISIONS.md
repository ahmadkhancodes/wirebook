# Decisions

Standing decisions are in docs/factory/BATCH1_PLAN.md (Mongo instead of Postgres, Better Auth, Stripe first, Mailer interface, Vercel-first, keep 3 deployments).

## 5 Nov 2026 (Phase 0)
- **Design direction:** workbook "Ledger and Terminal" adopted (docs/DESIGN.md). Competitor audit confirms the category look (dark glow, DM Sans/Inter, teal or blue pills); we differ on four axes.
- **Fonts:** Spectral + Public Sans + JetBrains Mono. Overrides the playbook's font whitelist under its ICP override rule; the ban list (Inter, Roboto, Arial, Helvetica, Open Sans) still holds.
- **Icons:** Phosphor (regular) instead of the workbook's Tabler, to follow the factory rule (Phosphor/Solar/Iconamoon) across all seven products.
- **Dark palette** is green tinted, not the playbook's neutral black list (one colour family). No gradients anywhere.
- **Queue:** Mongo collection behind a `JobQueue` interface; BullMQ/Valkey on the VPS later.
- **Sync wait:** long poll inside the held `sendRequestXML` (about 25 s) to reach "under 5 s warm"; sync API wait 90 s on Pro, 55 s on Hobby.
- **No real QuickBooks in build:** a spec faithful QBWC simulator + golden qbXML fixtures; real acceptance run is an owner item. Docs must not claim real world parity before it.
- **Banned deps CI** kept for unapproved vendors; approved exceptions: Vercel, Mongo Atlas, Stripe, Resend (mailer), Cloudflare R2/Workers.
- **Roadmap items** (webhooks, C#, MCP) are never shown as shipped on the site; "Coming in v1" line only.
- **Primary colour (orchestrator review, 5 Nov):** near-black ledger ink (#14201A / dark #E4ECE4), not green, to stay distinct from DockCrate, Stepclimb and Hotrail. Green kept only as band tint and success state. Design approved otherwise.
- **Before kit-v1:** build qbXML codec, QBWC SOAP handler and simulator as pure TS modules with tests, no UI. DB_DRIVER=memory until MONGODB_URI arrives.
- **qbXML specs are hand-authored (5 Nov):** the Intuit XSD is login-gated and not redistributable, so `src/lib/qbxml/spec.ts` declares element order for customer (query/add/mod) and invoice (query/add) from the public reference. Golden fixtures prove self-consistency only. M2 adds `tools/gen-qbxml` to verify/extend the specs against an XSD the owner downloads from Intuit, and the remaining ~35 objects. Not claimed as verified against real QuickBooks.
- **One job in flight per file** is enforced by the queue contract; Mongo driver must use a unique partial index on `(endUserId)` where `state='sent'` plus `findOneAndUpdate`. The memory driver's concurrency test caught a real check-then-set race, now fixed.

## 5 Nov 2026 (M2 bridge)
- **Status:** all M2 behaviour is validated against the simulator (`tools/simulate-qbwc`), never against real QuickBooks. Nothing here claims parity with a real Web Connector run.
- **Routes:** `/qbwc` (SOAP + `?wsdl`), `/v1/qbd/{object}[/{id}]`, `/v1/qbd/raw`, `/v1/requests/{id}`, `/v1/connect-links`, `/connect/<token>` (+ `/wirebook.qwc`, `/status`), `/errors/<slug>`. REST lives at `/v1/...` not `/api/v1/...` (the kit's `/api/v1/me` stays as is).
- **Tenancy:** a project is `{orgId}__{environment}`. The key's `metadata.environment` (set when the key is created in the dashboard) picks test or production; a key without it is a test key, so a legacy key can never reach production data. Every end user, request and idempotency key is scoped by projectId; test and production never see each other.
- **Bridge store:** one `Bridge` (queue, end users, sessions, idempotency, connect links) with a memory driver and a Mongo driver in `src/lib/bridge`; collections `requests`, `endUsers`, `qbwcSessions`, `idempotencyKeys`, `connectLinks`. The request log reads the `requests` collection, so a job and a request are the same record. The Mongo driver compiles and follows the memory contract but is not exercised by tests here.
- **3100 corrected:** 3100 is "name already in use" (code `duplicate_name`, 409), which the simulator and the site copy already said. `edition_not_supported` moved to 3250. The earlier mapping of 3100 to edition-not-supported came from the brief's shorthand and was wrong; the test was updated.
- **Error catalogue:** `src/lib/errors/catalogue.ts` is the single list (27 entries). Every entry has a page at `/errors/<slug>`; a test enumerates them against the route's `generateStaticParams` and against every code the mappers can produce. Guide slugs for QuickBooks codes are the number (`/errors/3140`). Thirty guides is still the launch target (M4 SEO pages).
- **Unified error object:** `{ error: { code, type, message, userFacingMessage, guideUrl (absolute), retryable, path?, requestId?, cursorExpiresAt? } }`.
- **Specs extended** (hand-authored, golden fixtures prove self-consistency only): vendor query/add/mod, item query + service item add, account query/add, bill query/add, receive payment query/add. REST keys: `expenseLines`, `itemLines`, `appliedTo`, `salesOrPurchase`. Update (Mod) exists for customers and vendors only; the other objects answer 405 `not_supported`. Items create service items only. The remaining ~33 objects and `tools/gen-qbxml` XSD verification stay M3.
- **Cursor pagination** uses the qbXML iterator (`Start`, then `Continue` with the id). The cursor is an unsigned base64url blob `{object, endUser, iteratorId, expiry}` valid 10 minutes, bound to the object and end user; it is not stored in `requests` (a stateless cursor needs no cleanup). Expired -> 410 `cursor_expired`, edited or foreign -> 400 `invalid_cursor`.
- **Idempotency:** header on writes, key scoped per project, body hash over method, path and canonical (key-sorted) JSON, 7 day expiry (Mongo TTL on a Date plus an expiry check at read). Same key + same request replays the original (marked `Idempotent-Replayed: true`, same request id, waits if still running); different request -> 409. A lost insert race cancels the loser's queued job.
- **Sync wait:** `waitMs` 55 s default (`SYNC_WAIT_MS`), poll every 250 ms, then `202` with `Location: /v1/requests/{id}`. `Prefer: respond-async` skips the wait. Long poll inside `sendRequestXML` stays off by default (`QBWC_HOLD_MS=0`): the Web Connector session ends when the queue empties, so a held request only helps once measured on a real rig (R2).
- **Raw passthrough** accepts JSON `{qbxml}` or an XML body, requires well-formed XML with exactly one request message, returns `{requestId, state, raw, parsed}`; a QuickBooks error still returns 200 with its `statusCode`. Raw jobs store the response on the request record (needed to return it); purge is M3.
- **Connect flow:** `POST /v1/connect-links {externalId, companyName?}` creates the end user (unique OwnerID, FileID, username; unique `(projectId, externalId)`), queues one cheap `customer.query` as the first-sync probe, and returns a link valid 24 h, single use (closed when the first sync is observed). Only the token hash is stored. Steps: 1 `.qwc` served, 2 first `authenticate` for that username (any result), 3 first `sendRequestXML` (the Web Connector reached QuickBooks, so the app is authorised), 4 first successful response. The Web Connector password is derived (HMAC of the end user id with `BETTER_AUTH_SECRET`) so the page can show it again; only its scrypt hash is stored, and rotating the secret breaks existing connections. A second link for an already synced file is refused (`already_connected`); reconnect links come with the health monitor in M3.
- **Request log** is now `/app` (the kit's overview page is gone; plan and usage stay on `/app/billing`). Server rendered, filters via GET, detail pane via `?req=`, keyset paging via `?before=`.
- **Connect page theme:** follows the site theme (light and dark both checked) instead of light only.
- **E2E-only helper:** `/api/dev/seed-requests` (404 unless `E2E_OUTBOX=1`) fills the log for the screenshots.

## 5 Nov 2026 (M3)
- **Active file = a production-environment file with one successful sync in the calendar month (UTC).** Counted once via `markActiveFile` from the `/qbwc` success hook; test/sample files never count. The connect-flow probe counts too (it proves the file answers).
- **Developer cap:** 3 active production files; the 4th is refused at request and connect-link time with 402 `file_limit_reached` (new catalogue entry). Paid plans are not capped, they are billed. Reading product.ts "3 non-production files" as 3 included files.
- **Pricing math (`chargeFor`):** Production per file; Starter Pack = pack price for 4 files plus Production's per-file rate above 4; Volume = max(files, 50) x $16.99 (50 file floor, monthly only). Annual shown as 12 x per-file annual rate.
- **Stripe quantity:** Production/Volume update the subscription item quantity; Starter Pack keeps the pack at 1 and puts extra files on a Production priced item added to the same subscription (quantity 0 when none). Only subscriptions with `metadata.app=wirebook`. Sync runs when a file first becomes active; billing errors never fail the SOAP reply.
- **Health:** Asleep after 2 h without a poll, Broken after 72 h or on a Web Connector connection error (thresholds in `product.health`). Recovery happens in `authenticate`. `brokenNotifiedAt` gives one email per incident; only production files email. The list also applies the same rule at read time so it is right between ticks. No 2-check anti-flap yet (brief mentions it): the 2 h threshold is far above the poll interval.
- **Reconnect:** `POST /v1/connect-links` now works for Asleep/Broken files (409 `already_connected` only when healthy); a reconnect replays the four observed steps. The dashboard action only creates the link (we hold no end-user email).
- **Retention:** `product.retention`: payloads 14 days, metadata 90. The purge clears body, parsed result and raw response (not only raw), keeps metadata, writes an audit entry per sweep. Orgs can only shorten (1 to 14 days).
- **Dashboard transport:** polling every 5 s instead of SSE (Vercel function limits); revisit on the VPS.
- **`tools/gen-qbxml` skipped:** the new specs are ~15 lines each and the Intuit XSD is login-gated, so a generator would not remove work. Date-driven terms not done. Known wart: API keys `pONumber`/`aRAccountRef` from the camelCase rule.
- **OpenAPI** is generated from the qbXML specs converted to Zod 4 (`z.toJSONSchema`), so new objects appear automatically. `info.license` is a placeholder.
- **SDKs:** `@wirebook/sdk` (npm workspace, zero deps, MIT) and Python `wirebook` (stdlib only, MIT); no third-party libraries added. Python tests run with `python3 -m unittest discover -s tests` (Python 3.14 here). `revision_conflict` maps to ConflictError; a slow list throws `request_pending` rather than a truncated page.
- **Playwright browser** had to be installed in CI (`npx playwright install chromium`).

## M4 (webhooks, update operations, abuse controls, docs, dashboard polish, retention)
- **Webhooks:** the kit module is kept (HMAC `t=<unix>,v1=<hmac of "t.body">`, 8 attempts with backoff 30 s to 12 h, delivery log, 90 day TTL). New: each endpoint listens to ONE environment (`test` or `production`; older endpoints without the field hear both), events `request.completed`, `company_file.connected`, `company_file.broken`, `usage.threshold_reached` (80% and 100%, once per meter and period via a usage counter) and `test.ping`, plus delivery replay (`POST /api/webhooks/deliveries/<id>/replay`, audited) and a body viewer. Payloads carry ids and statuses only, never QuickBooks data. Events leave the bridge through an optional `onEvent` hook on `handleSoap` (`src/lib/webhooks/events.ts` is the sink), so the bridge stays free of the database and moves to a VPS unchanged. A broken sink never fails the SOAP reply.
- **Cron limits:** `vercel.json` already carries `webhook-retries` (daily) and `purge` (daily): that is the Hobby limit of 2 crons, once a day each. Nothing was added. Per-minute retries come from the Cloudflare Worker (`JOBS = "webhook-retries,health-tick"` in `infra/cron-worker/wrangler.toml`, already there); until the worker is deployed a failed delivery waits up to a day. Listed in MANUAL_STEPS.
- **Update operations:** `invoice, bill, estimate, sales-order, sales-receipt, credit-memo, purchase-order, item (service), account, terms` now have Mod specs, hand-authored like the rest, derived in `spec.ts` from the Add specs (every field optional, id plus `revisionNumber` required, lines become `XxxLineMod` with a required `txnLineId`, `-1` adds a line). Payments still answer 405 `not_supported` (ReceivePaymentMod needs applied-to handling we did not want to guess). Transactions are addressed by `txnId`. Golden fixtures in `tests/update-ops.test.ts` prove self-consistency only. The simulator gained transaction Mod handling and an EditSequence on transactions.
- **Typed SDK models:** `tools/gen-sdk-models` reads the same specs (`npm run gen:sdk`) and writes `packages/sdk-ts/src/models.ts` and `packages/sdk-py/src/wirebook/models.py` (TypedDicts). `<Name>Create`, `<Name>Update` (no id) and `<Name>` rows. `tests/sdk-models.test.ts` fails when the committed files are stale. The TS `Resource` is now `Resource<Row, Create, Update>` (`never` for payments); Python `Resource` is generic over the same three.
- **Abuse controls (`src/lib/security/abuse.ts`):** per source address 1,200 requests a minute (before the key is read), per key 600 a minute, 10 bad keys a minute per address, and a fair-use daily cap per organization and UTC day by plan (`product.abuse.dailyRequests`: Developer 5,000, Production and Starter Pack 250,000, Volume 1,000,000, test and production together). 429 answers carry a message with the number, `Retry-After` and `X-RateLimit-*`. New catalogue codes `daily_cap_reached` (429), `org_suspended` and `key_suspended` (403), each with a guide page. Because of the cap the pricing highlights no longer say "unlimited test API calls" or "unlimited API usage": they state the daily cap. This is a change from brief.md and was made on the owner's request for a daily cap.
- **Suspension:** stored in `org_settings` (`suspended`, `suspendedKeys`), checked on every API request; admin page `/admin/abuse` (founder accounts only) with `POST /api/admin/suspend`, every action audited with the actor.
- **Sign-up checks:** `POST /api/auth/sign-in/magic-link` (which is also sign-up) goes through `checkSignup` first: the `signups_enabled` flag, address validity, disposable-domain blocklist (also kept in the Better Auth user-create hook), per IP and per address limits, then a solved ALTCHA challenge in the `x-altcha` header (single use). The browser solves it with `altcha-lib` and Web Crypto (about a second); no widget package is used. Side effect: `signups_enabled=off` also stops existing users from requesting a link, since the two cannot be told apart before the link is sent. E2E specs fetch and solve a challenge with `tests/e2e/altcha.ts`.
- **Retention:** the purge already removed bodies, parsed results and raw responses at the org's setting. New: saving a shorter setting applies at once to what is stored (both environments) with a `retention.purged` audit entry (`trigger: setting_changed`), and request rows themselves are now deleted after `metadataDays` (90) by the daily job with a `retention.metadata_deleted` audit entry. The privacy policy, DPA, security page and landing FAQ no longer say "payload logging is off by default" (payloads are stored for up to 14 days); they now describe the 14 and 90 day deletion. Legal wording still needs the owner's review before launch.
- **Dashboard:** request detail has copy as curl (the key is a placeholder; a purged body is flagged, not invented), copy request id, a link to the company file and the stored request body and result while retention holds them. The company file page has a sync history (last 25 requests). `/app/usage` draws requests per day (30 days, with the plan's cap line) and active files per month (6 months) as plain SVG with a "show the numbers" table; no chart library. Loading skeletons added for usage and company file pages.
- **Docs site:** `/docs` pages for resources (one per object, built from the field specs), idempotency, webhooks, SDKs, limits, retention and troubleshooting (QuickBooks codes from the catalogue) plus llms.txt, all stating that behaviour is validated against the simulator.

## M5 (pre-launch review, 7 Nov 2026), see docs/REVIEW.md
- **Billable file = not a QuickBooks sample company file, in either environment.** The Web Connector reports `strCompanyFileName` on `sendRequestXML`. We store it, and a basename `sample_*.qbw` marks the file as a sample (`EndUser.sampleFile`). Sample files are free with test or production keys; any other file counts as active and is capped on Developer, whichever key is used. Before the first `sendRequestXML` the environment decides, as before. This replaces the M3 rule "test environment = free", which let real workloads run unbilled on `sk_test_` keys. Known gap: renaming a real file to `sample_x.qbw` passes. Confirm the sample file names on the real install and consider the company-info fingerprint the brief mentions.
- **Plan gate runs twice:** at request time (`checkFile`, now given the end user) and when the Web Connector asks for work (the new bridge hook `admit`). A refused file's queued requests fail with 402 `file_limit_reached` and nothing reaches QuickBooks. `recordActiveFile` never records a file beyond a capped plan's allowance. The hook fails open on errors, so billing never stalls a sync.
- **Stuck requests:** a request `sent` for more than 15 min (`SENT_TIMEOUT_MS`) becomes `outcome_unknown`, from the file's next `sendRequestXML` and from the `health-tick` sweep. It is never retried automatically. `connectionError` marks an in-flight write `outcome_unknown` (a read stays `failed`). A reply whose `requestID` does not match the in-flight job is ignored.
- **Idempotency reserves the key before queueing**, under a pre-generated request id (`newRequestId`, uuidv7). `JobQueue.enqueue` accepts an optional `id`, and a duplicate id collapses to the existing job. The memory queue orders by insertion instead of by id.
- **Secrets:** `secretOr()` throws in production when `BETTER_AUTH_SECRET` (and the derived ALTCHA and unsubscribe secrets) is missing, instead of using the public dev fallback.
- **Webhook deliveries resolve the host** and refuse private addresses (`blocked_address`).
- **API key roles:** owner and admin get `apiKey: create/update/delete` (what Better Auth's api-key plugin checks), next to the `manage` our UI uses.
- **Stripe quantity** is also synced on every relevant Stripe event (upgrade, change), not only when a new file activates.
- **Copy:** "we reconcile by RefNumber" is removed (no such feature). Webhooks are shipped, the connect link lasts 24 h, Developer is "up to 3 real company files a month", and QuickBooks 2024 is "target version, validated against the simulator".
- **Indexes auto-create on first Mongo getDb():** fire-and-forget, memoized per instance, never blocks or fails a request (warn + retry next cold start); index conflicts (codes 85/86) are logged and skipped. The health route doesn't use getDb(), so it is unaffected.

## Launch hardening (10 Nov 2026)
- **Downgrade mid-month:** no change. The file meter is per calendar month, so files already active keep working until the month ends; the cap applies again from the 1st. Simpler to explain than a mid-month cut-off, and the cost to us is bounded by one month of a few files.
- **SDK names:** `@wirebook/sdk` (npm) and `wirebook` (PyPI). MANUAL_STEPS item 5 updated.
- **Revoke is final:** a revoked company file cannot be reconnected; create a new end user with a new `externalId`. Avoids a password-version scheme.
- **Mail failures never fail the request** (`sendMailSafe`); the cost is a silent no-send, covered by the `mail_send_failed` log.
